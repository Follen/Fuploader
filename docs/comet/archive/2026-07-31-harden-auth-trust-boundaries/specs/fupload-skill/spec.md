# Fupload Skill 完整目标规格

## 激活与定位

Skill 的显示名为 `Fupload`，安装名保持 Skill 规范允许的 `fupload`。它只能由用户显式调用；
普通对话即使提到插件、NewBee 或 DD，也不得自动进入 Fupload 工作流。显式调用后，Skill
是唯一主交互层，Python CLI 只是原子工具。

Skill 不提供、暗示或调用 delete；验证结束后的测试对象清理由仓库 `analyze/` 流程负责，
不属于可分发 Skill 的能力或用户工作流。

## 意图和平台

用户未说明动作时只问一次人话菜单：选择 NewBee 或 DD，以及插件、配置、WA/字符串的
创建、内容更新或资料编辑。用户已说明时直接调查，不重复问菜单。

Skill 将自然语言映射为统一语义：

- create：创建主对象；需要首版内容时编排后续 update；
- update：插件新版本、配置备份内容更新、WA 字符串新版本；
- edit：名称、说明、分类、图片、商业、关联、频道与公开/审核设置。

## 调查、补齐与确认

Skill 先读取对应 `references/` 字段矩阵和叶子命令 help，再检查用户工作区中的 TOC、
README、CHANGELOG、Git 变更、压缩包和媒体。远端目标、当前详情、分类、版本、备份、
频道、会员、关联候选全部用只读 CLI 查询；可查事实不得让用户手抄。

每个字段在 references 中明确动作阶段、平台名、类型、是否必填、条件、清空语义和动态
来源。Skill 只询问本地与远端都无法决定的产品选择。候选不唯一时展示名称、ID 和关键
区别；不根据旧 manifest、相邻字段或行业默认猜值。

任何网页表单可选业务字段都交给用户选择。Agent 可以根据用户已经明确给出的资料整理
建议，但不得静默接受网页预选项；动态字段先用 CLI 查询候选，再以人话展示并取得选择。

写入前在被发布项目根目录创建 `publish/<YYYYMMDD-HHmmss>-<platform>-<resource>-<action>/`，
重名时依次追加 `-2`、`-3`。同一次发布计划的原子命令 JSON 按执行顺序保存为
`01-<action>.json`、`02-<action>.json`；重试和读回继续使用该目录，独立的新发布计划必须创建
新目录。该目录不得创建在 Skill 内或 Skill 旁边，执行后作为项目发布记录保留；除非用户明确
要求，不修改项目忽略规则。必要时 dry-run，然后用人话一次展示完整计划：平台、资源、目标
ID、原子步骤、所有将改变的字段、保留/清空项、文件、版本、备份、商业设置和公开审核影响。
取得一次确认后串行执行，之后不重复询问同一计划。

## 执行与恢复

每个原子命令成功后立即使用 get/list/history 读回。任一步失败停止后续步骤，报告已成功
动作、保留对象/媒体、远端 ID、失败原因和最小重试入口。网络结果不确定时先读回，不直接
重发。服务端接受审核不描述为审核通过。

NewBee 配置要求用户已在客户端上传云备份；没有备份时提示用户完成客户端上传后继续。
DD 配置同样从 DD 云备份列表选择，Skill 不绕过官方备份来源。更换备份时重新整理与该
备份匹配的全部选择和增量更新项。

选择 DD 时，Skill 先调用 session doctor。Python 自动寻找 DD 安装目录和官方无头客户端；
只有自动发现全部失败时才向用户询问安装路径。不得要求用户提供 token、clientNo 或
`cred.db`，也不得调用 Computer Use。

## 文档完整性

Skill 包内 references 必须完整列出 NewBee/DD 三类资源的 create/update/edit 字段、动态
GET 依赖、阶段锁定、条件清空、审核状态、上传协议和读回策略。引用按动作渐进加载，避免
把全部字段一次塞入上下文，但任何字段都能由对应 reference 找到，不依赖仓库 `analyze/`。

Skill 包复制到另一台机器后，只依赖包内 Python 源码和对应官方桌面客户端状态即可审计、
查看 help 和执行；不得引用仓库外的 Go binary、探索报告或作者本机绝对路径。

Skill 必须指导 Agent 从动态接口枚举当前全部游戏 build，并按 build 隔离版本、分类、备份和
资源引用；不能把某一 build 的候选沿用到另一 build。references 覆盖 CLI 暴露的全部叶子接口、
真实验证步骤、预期拒绝、最终一致性等待、受限前置条件和保留对象恢复方式。

交付前按真实 help/schema 对 Skill 与 references 做完整性审计，并模拟主资源、附属接口、上传
失败、网络不确定、无备份、无分类、空列表、跨 build 输入和审核状态边缘流程。发现缺口后更新
代码和 Skill，再执行回归与复审，最终验证报告列出全部接口和 build 的结论。

## Doctor 信任诊断

NewBee doctor 自主使用 Windows Known Folder 下的官方 auth-store，并验证内置 Creator、认证、
metadata、next API 和上传 origin；它不从项目、环境变量或远端响应发现认证目标。DD doctor
继续自主发现官方客户端安装目录，但启动前验证 Authenticode 链和官方发布者。

doctor 的稳定 JSON 诊断包含规范化 origin、路径来源、安装版本、签名状态、发布者和认证布尔
结果。它不得返回凭据内容、token 长度/哈希、clientNo、Cookie、JWT、原始 WA、备份内容或
足以重放认证的字段。信任验证失败时在任何敏感请求或 executable 启动前停止，并给出可操作
但脱敏的失败原因。
