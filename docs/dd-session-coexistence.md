# DD 会话共存调查

日期：2026-10-30。工作分支：`codex/dd-session-coexistence`。

## 已确认的旧行为

1. 1.0.2 在 DD 界面运行时仍会执行一次原生桌面登录。手机号走 `MobileReLoginFlow`，邮箱走 `UrsReLoginFlow`，随后均调用 `LoginController.startLogin`。
2. 登录控制器新建会话，向消息服务器握手时使用桌面 `clientType=412`。独立设备号没有消除这次桌面登录。用户报告它会将原客户端账号顶下线；此前“窗口仍在”未验证账号共存。
3. `MessageCenter.logout()` 本身只断开自己的消息连接，没有发现它调用全账号退出接口的证据。因此不能把顶号直接归因于这个函数。
4. 安装包 `Start.exe` 的清单为 `requireAdministrator`，`netease_dd.exe` 为 `asInvoker`。本机 DD 主进程实际为高完整性，普通终端直接读其进程内会话会被 Windows 拒绝，错误 5。

调查使用 DD 100130：`ccvoicehub.res` SHA-256 为 `953b1bd893adb53c8b003d490ee219fe4a0e075efbed960fc8bc1bcff2a26892`，内嵌 Python 为 3.7.17。

## 字节码还原

旧 `pydisasm` 输出把若干导入、存储等操作读成了不相干的指令。通过将相同源码分别交给 DD 内嵌编译器及标准 CPython 3.7 编译器，比较递归代码对象的指令长度与操作数，建立了 107 条原生指令的映射。校正后可读取登录握手、Cookie 更新、JWT 和退出调用。

研究脚本及静态结果位于本工作树的 `analyze/dd-coexistence/`，按仓库约定忽略。没有把凭据放进这些记录。

## 采用的普通权限方案

DD 的 WebView2 网络子进程实际以普通权限运行。它持有当前账户浏览器 Cookie 数据库的文件句柄，可以在同一用户权限下复制句柄并建立只读映射，无须读取高权限 DD 主进程的内存。

流程为：验证 DD 与 WebView2 签名及父子进程关系，绑定活动 profile，读取 Cookie 数据库和已提交 WAL 的内存快照，用 DPAPI/CNG 解密现有 `NTES_YD_SESS`，通过匿名管道交给 DD 原生 HTTP 签名器。然后仅执行作者 HTTP 认证和发布请求，跳过原生聊天登录。

Cookie、密钥和数据库快照只保留在内存，不写入文件、参数、环境变量或日志。复用失败时直接报错，不创建另一条桌面登录。没有注入代码、远程线程、进程内存写入或界面操作。最初尝试的管理员进程内存读取原型不属于采用的方案。

## 实际验证

- 普通权限终端复用当前 DD Cookie，作者登录及本人插件列表查询成功。
- 新 CLI `dd session start` 返回 `session_source=desktop-cookie`、`native_login_count=0`。通过 broker 读取作者列表后，停止返回 `logout_requested=false` 和 `cleanup_complete=true`。
- 上传隔离测试 ZIP，下载内容与原包逐字节一致。未新建或修改公开插件记录。
- DD 原有的一条已建立 TCP 连接在上传中，以及结束后 10、20、30 秒均保留，GUI 进程 PID 没有变化。这验证了连接保持；不能将它扩大为所有服务状态和所有账号的长期验证。
- 后续检查中，这条连接的创建时间仍为 18:37:32，包含上述测试期间，没有发生重连。两个独立作者 HTTP 客户端也已验证：第二个客户端认证及关闭后，第一个客户端仍能正常读取作者列表。
- 原生邮箱及三种手机号凭据分流测试仍通过。当前 Cookie 路径不按手机号或邮箱分流；独立邮箱账号的实机测试尚未执行。

## 当前边界

CC 频道查询需要另一类 JWT。后续开发已新增固定版本的只读运行时辅助，仅频道查询需要读取 GUI 内存；高权限 GUI 对该操作要求同用户管理员终端，普通上传仍不需要。辅助不触发第二次桌面登录，目前已通过本地 mock 与独立 Qt 夹具，真实 GUI 管理员验收仍待回传。当前完整契约见[平台字段总表](../fupload/references/platform-fields.md#dd)。

普通权限、真实上传和无原生重登录已验证；尚未对另一邮箱账号、长时间会话续期、客户端切换账户以及真实插件版本发布完成完整回归。本次调查不自动合并或发布 npm。
